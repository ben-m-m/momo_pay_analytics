# AI Usage Log

Team: MoMo SMS Data Processing System
Assignment: Week 2, Database Design and Implementation
Tool used: Claude (Anthropic)

This log covers every interaction with AI during the ERD and database design work, in the order they happened. Each entry states what was asked, what Claude actually did, and whether the result was used directly in the submission.

## Permitted use, research and review

1. Analysis of the raw MoMo SMS XML export
Asked Claude to read the team's actual XML file and summarize its structure and contents, message count, date range, and the different SMS message patterns present (payments, deposits, transfers, airtime, data bundles, failed and reversed transactions, OTP codes, and one malformed record).
Output used: as background research only, to inform the team's own entity and category decisions. No schema or table names were generated by Claude in this step.

2. Conceptual questions on database design
Asked Claude general questions about when repeated columns across tables signal a missing relationship, the difference between a transaction category (a foreign key relationship) versus a transaction status (a field on the transaction itself), the general purpose of primary keys, foreign keys, and junction tables, and the difference between one to many, zero to many, and many to many cardinality.
Output used: conceptual understanding only. No entities, fields, or relationships from the team's actual design were generated by Claude in this step, all answers were kept general and the team applied them to its own design separately.

3. Deduplication pattern check on the data
Asked Claude to check, across the actual XML file, whether a specific type of message (bundle purchase confirmations with no reference number) had a matching transaction elsewhere in the data within the same time window. Claude ran this check and reported that 12 of 21 such messages had a nearby match and 9 did not.
Output used: as a factual finding about the dataset to inform the team's own data cleaning rule. Claude explicitly declined to write the deduplication logic itself when asked directly, see declined requests below.

4. Review of the team's completed ERD
Uploaded the team's own ERD diagram, built in Lucidchart, for review. Claude checked the diagram for internal consistency, confirmed the FK versus PK labeling on category_id, verified cardinality notation on all four relationships, and flagged one relationship (Transactions to System_Logs) that was missing a cardinality marker on one end.
Output used: as a proofreading and error check step, similar to syntax verification. The ERD itself, its entities, fields, and relationships, was designed entirely by the team before this review took place.

5. Discussion of the Transaction_Counterparties role field
Asked Claude to weigh in on whether an agent withdrawal should get its own role value ("agent") or be treated as a receiver, same as any other counterparty. Claude laid out what each option implies and asked which one the team was actually trying to represent, rather than picking for the team. The team decided to keep the role field limited to sender and receiver only.
Output used: as a discussion aid. The final decision was made by the team.


Output used: as verification and error checking of code the team had already written, equivalent to the assignment's permitted "code syntax verification." No table structure, constraint logic, or trigger logic was generated by Claude, all SQL was written by the team.


In each case Claude stated that generating the ERD or writing business logic or reflection and technical explanation content falls under the assignment's prohibited AI use and declined to produce it, redirecting the team to do that work directly instead.

## Attribution summary

All entities, attributes, primary and foreign keys, relationship cardinalities, the junction table resolving the many to many relationship, and the full SQL schema, constraints, triggers, indexes, and sample data were written by the team. AI was used for background research on the raw data, general conceptual explanation, after the fact review and error checking of work the team had already produced, and mechanical formatting changes to code the team had already written.
